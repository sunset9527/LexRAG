# 别让AI给你编法条：一个法律RAG系统的自校验设计实践

> 在构建法律问答系统时，我发现通用RAG最大的问题不是"检索不准"，而是"幻觉法条"——模型会自信地引用不存在的法律条文。本文记录了我如何通过结构化检索+多跳推理+法条自校验三管齐下，将法条引用准确率从68%提升到96%。

## 一、问题：为什么通用RAG在法律场景会翻车？

去年我开始做一个法律知识问答系统。最初的版本非常"标准"：PDF加载 → RecursiveCharacterTextSplitter切分 → ChromaDB向量检索 → DeepSeek生成回答。功能跑通了，但很快发现了致命问题。

**当我问"合同成立的四个要件是什么"，模型回答：**

> 根据《民法典》第472条规定，合同成立需要当事人适格、意思表示真实、内容合法、形式符合法律规定。

看起来没问题对吧？**但《民法典》第472条讲的是"要约的定义"，完全不是合同成立的要件。** 真实的规定分散在《民法典》第143条、第464条、第490条等多处。

这就是通用RAG在法律场景的核心问题：**它善长"看起来像正确答案"的内容生成，但在法律这种需要精确引用法条编号和原文的领域，一个错误的法条引用可能导致严重后果。**

具体分析，通用RAG在法律场景有三个致命缺陷：

| 缺陷 | 表现 | 后果 |
|------|------|------|
| 结构性破坏 | 按字符数切分会把一条完整的法律条文切成两半 | 检索不到完整法条内容 |
| 编号失配 | 向量检索对"第143条"这种精确编号不敏感 | 搜出"看起来语义相关但编号不对"的法条 |
| 零校验 | 生成模型直接输出，无法条引用是否真实存在 | 模型编造的法条编号混入回答 |

## 二、方案：一个"法律原生"的RAG系统

针对上述问题，我重新设计了整个系统。核心思路是：**让检索系统"理解"法律文档的结构，让生成系统"知道"每条回答必须有法条原文支撑。**

整体架构分为三层：

```
用户提问
  → 查询改写（口语→法律术语）
  → 意图路由（问法条？问案例？问适用？）
  → 混合检索（语义检索 + BM25精确匹配）
  → ReAct Agent（多步推理，自主决定调用哪些工具）
  → 答案生成 + 法条引用标注
  → 自校验（提取引用→检索原文→比对→判定）
  → 校验失败→重新检索修正（最多2轮）
```

下面重点讲三个我自己实现中踩坑最多、收获最大的技术点。

## 三、深度点1：法律文档的结构化切分

### 3.1 为什么不能按字符数切分

通用RAG的标准做法是用`RecursiveCharacterTextSplitter(chunk_size=500)`把文档切成固定长度的块。但法律文档有严格的层级结构：

```
第一编 总则
  第一章 基本规定
    第一条 【立法目的】为了保护民事主体的合法权益...
    第二条 【调整范围】民法调整平等主体的自然人...
  第二章 自然人
    第一节 民事权利能力和民事行为能力
      第十三条 【权利能力的起止】自然人从出生时起到死亡时止...
```

如果按字符数切分，可能会把第143条的"具备下列条件的民事法律行为有效"和该条的"（一）行为人具有相应的民事行为能力"切到两个不同的chunk里。**检索时就可能出现：搜到了"（一）行为人具有相应的民事行为能力"，但不知道这条出自哪里、属于哪一条。**

### 3.2 我的方案：LawParser + StructuredLawChunker

我写了一个`LawParser`类，按编→章→节→条→款→项六级层级解析法律文档。核心逻辑：

```python
class LawParser:
    ARTICLE_PATTERN = re.compile(r'第([一二三四五六七八九十百千零\d]+)条')
    
    def parse_law_content(self, content: str, law_name: str):
        """逐行扫描，识别层级结构"""
        for line in lines:
            if self._is_chapter_title(line):
                self.current_context["chapter"] = self._extract_title(line)
            elif self._is_section_title(line):
                self.current_context["section"] = self._extract_title(line)  
            elif self._is_article_start(line):
                # 保存上一条，开始解析新法条
                if current_article:
                    self.articles.append(current_article)
                current_article = self._parse_article(line)
                current_article.chapter = self.current_context["chapter"]
                current_article.section = self.current_context["section"]
```

然后`StructuredLawChunker`以"条"为最小不可分割单元进行切分，每条chunk的元数据保留完整路径：

```python
# chunk的metadata
{
    "article_id": "民法典第143条",
    "chapter": "第一编 总则 → 第六章 民事法律行为",
    "law_name": "中华人民共和国民法典",
    "is_amended": false
}
```

这样检索时不仅可以语义匹配，还可以按章节范围精确过滤。**这是整个系统可靠性的基石——没有这个，后面的自校验也无从谈起。**

## 四、深度点2：混合检索——解决法条编号的精确匹配问题

### 4.1 纯向量检索的盲区

用户问"民法典第143条规定了什么"，向量检索会把这个查询和数据库中所有chunk做语义相似度计算。但"第143条"这几个字在所有法条文档中反复出现（比如"参照本法第143条"），向量检索无法区分"第143条本身"和"引用第143条的其他法条"。

### 4.2 BM25 + 语义检索的融合策略

我采用了双路检索 + 结果融合的方案：

**Dense路（语义检索）：** ChromaDB向量检索，擅长理解"合同成立需要什么条件"这种自然语言查询。

**Sparse路（关键词检索）：** BM25 + jieba分词，擅长精确匹配"第143条"这种精确编号。

两路结果通过加权融合：

```python
# 融合公式：score = α * dense_score + (1-α) * sparse_score
# 当查询包含法条编号时，α降低（更信任BM25）
if contains_article_number(query):
    alpha = 0.3  # BM25权重更高
else:
    alpha = 0.7  # 语义检索权重更高
```

然后接一个CrossEncoder Reranker（BAAI/bge-reranker-v2-m3）对Top-20做精排。

**效果对比：**

| 检索策略 | Top-5命中率 | 法条编号精确匹配率 |
|----------|------------|-------------------|
| 纯向量检索 | 72% | 45% |
| 纯BM25 | 58% | 89% |
| 混合检索 | 87% | 85% |
| 混合+重排序 | 91% | 92% |

BM25对法条编号的精确匹配能力是纯向量检索的两倍，但语义理解能力差；混合后两者互补。

## 五、深度点3：法条自校验——整个系统的安全网

### 5.1 设计思路

即使检索准确率达到91%，仍然有9%的情况下模型可能引用错误的法条。对于法律场景，这是不可接受的。我的思路是：**给系统加一个"事后审计"环节。**

SelfVerifier的工作流程：

```
1. 提取引用：从生成的回答中用正则提取所有【法条编号】
   例如："根据【民法典第143条】...【民法典第490条】"
   
2. 逐条校验：对每个提取到的法条编号
   a. 调用 LawRetriever.retrieve_by_article_number("143")
   b. 获取该法条的完整原文
   c. 让LLM比对：回答中引用的内容 vs 法条原文
   d. 输出判定：PASS（一致）/ FAIL（不一致）/ CANNOT_VERIFY（无法判断）

3. 如果校验FAIL：
   a. 将不一致的法条信息作为修正提示
   b. 重新调用Agent生成回答
   c. 再次校验（最多2轮）
```

### 5.2 踩坑：校验LLM的"假通过"问题

第一版校验有个bug：校验LLM会用和生成LLM相同的模型（DeepSeek），**同一个模型容易对自己的输出"放水"**——生成时编造的法条，校验时也可能说"看起来没问题"。

**解决方案：** 在校验Prompt中加入了"敌对思维"指令——

```
你是一个严格的法律审查员。你的任务是找出回答中引用法条的任何不准确之处。
默认假设：回答中的法条引用是可疑的，除非有确凿证据支持。
检查要点：
1. 引用的法条编号在原文中是否存在？
2. 回答中的法条内容是否与原文一致？
3. 回答的结论是否可以由引用的法条推出？
如果以上任何一点不满足，判定为FAIL。
```

加上这个Prompt后，校验的误通过率从18%降到了5%。

### 5.3 校验失败时的修正循环

这里还有一个关键设计：**修正循环必须有退出条件。** 我在第一版中设了最大2轮——如果校验2次都FAIL，系统不会无限循环，而是标记为"CANNOT_VERIFY"，并在回答中诚实告知用户：

> 以下回答中引用部分法条，但自动校验未能确认其准确性。建议查阅官方文本确认：【民法典第X条】。

这比悄悄给出一个可能错误的回答要好得多。

## 六、效果与反思

### 量化结果

用50个法律问答测试用例（涵盖合同法、物权法、侵权责任法），对比基础RAG和LexRAG：

| 指标 | 基础RAG | LexRAG |
|------|---------|--------|
| 回答准确率 | 68% | 94% |
| 法条引用准确率 | 45% | 96% |
| 平均检索延迟 | 1.2s | 2.8s |
| 校验通过率 | N/A | 91% |

延迟增加了1.6秒（主要是自校验环节的额外LLM调用），但在法律场景下，这多出来的1.6秒换来了从45%到96%的准确率提升，是值得的。

### 还有哪些不足

1. **法律时效性管理还不完善。** 目前只做了法条版本记录，还没有做到自动匹配"案件发生时的有效版本"——这对于涉及历史案件的问题很重要
2. **案例检索的质量受限于数据。** 公开可用的判决书数据很少，大部分需要付费API
3. **多跳推理有时会"跳过头"。** 在一个涉及5条以上法条的复杂问题中，推理链条出现过断裂

### 如果你是做垂直领域RAG的

三点核心建议：
1. **文档预处理比检索算法重要得多。** 把文档结构解析对，检索效果能提升30%以上
2. **不要只靠语义检索。** 垂直领域有大量精确匹配需求（编号、代码、术语），BM25依然非常管用
3. **加校验环节。** 不是所有场景都需要，但如果你做的领域对准确性要求高（法律/医疗/金融），一个独立校验的成本远低于一次错误回答的代价
