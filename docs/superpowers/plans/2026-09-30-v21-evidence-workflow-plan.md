# LexRAG v2.1 实施计划：证据驱动法律工作流

**状态**：代码与自动化验证完成；2026-09-30 因未配置有效 LLM Key、Redis 未启动，经决定跳过真实 LLM 端到端验收。

> 基于 `2026-09-30-v21-evidence-workflow-design.md`。每项生产代码均遵循 Red → Green → Refactor：先新增最小失败测试并确认失败原因，再写最小实现。

## 1. 证据账本与确定性引用校验

1. 新建 `tests/test_evidence_workflow.py`，覆盖证据去重、跨知识库隔离、缺失身份字段拒绝入账、同库同法律同条号引用通过、伪造条号/错误法律名/无引用失败。
2. 运行该测试，确认因工作流模块不存在而失败。
3. 新建 `src/workflow/evidence.py`：定义 `EvidenceItem`、账本构建、规范化条号、引用解析和规则校验结果；实现不依赖 LLM。
4. 再次运行目标测试，确认通过。

## 2. 固定节点的单工作流

1. 为简单问题跳过拆解、路由失败回退法规检索、案例/图谱失败降级、轨迹脱敏、校验失败最多修复一次补充失败测试。
2. 运行测试，确认失败原因是工作流节点尚不存在。
3. 新建 `src/workflow/legal_evidence_workflow.py`：实现 planning、routing、法规必跑的检索扇出、账本、答案、校验和一次修复节点。LangGraph 仅用于状态机编排，不调用 `create_react_agent`。
4. 通过构造函数注入检索、LLM 和时钟依赖，使单元测试可使用真实账本逻辑和小型替身，不触发外部模型或 Chroma。
5. 运行 v2.1 测试及既有检索/自校验测试。

## 3. `/query` 接入与缓存边界

1. 扩展或新建 API 契约测试，验证 metadata 含脱敏工作流摘要、校验失败结果不写缓存、既有缓存命中仍兼容。
2. 先运行测试，确认失败。
3. 将 `api.py` 的请求级 `LegalRAGWorkflow` 迁移为 v2.1 工作流，同时保留旧类供未迁移调用方使用；按当前 READY 知识库构造法规检索器，并尽可能注入同库案例/图谱检索器。
4. 在缓存写入前检查 `verification_status`，仅缓存规则验证通过的结果；保留 Redis 故障旁路。
5. 运行缓存与 API 回归测试。

## 4. 前端工作流摘要

1. 检查现有聊天 API 类型和界面状态；新增 metadata 的 TypeScript 类型。

3. 执行 TypeScript 检查和生产构建。
