# Stage 4：按案件日期选法、版本展示与案例来源审计

日期：2026-10-25

## 目标

完成 Stage 4 余下的最小用户闭环：问答可以按案件发生日期选择有效法规版本；用户可以在结果中看到该选择及来源版本；案例资料可明确显示关键字段是否缺失。

## 范围与边界

- `/query` 接收可选 `case_date`（ISO `YYYY-MM-DD`）。提供日期时，只检索在该日期有效且已完成版本链核验的法规版本。
- 未提供日期时，按服务当前日期选择版本，并在响应中返回“未提供案件发生时间，按当前有效法规检索”的假设说明。日期无适用版本或存在多个有效版本时，返回可识别的失败原因，不回退到不确定版本。
- 引用与检索证据返回已有的五项版本溯源字段：`version_id`、`effective_from`、`effective_to`、`source_url`、`content_hash`。前端将其渲染为适用版本卡片，并以只读时间线展示同一法律已登记版本链。
- 案例来源接口返回案号、法院、裁判日期、裁判要旨的完整性状态及 `missing_fields`。系统不推测、不补写原始案例缺失字段。

## 不做的事

- 不做未经完整历史全文支持的逐条版本差异。
- 不做人工“回退索引”操作；已存在的隔离 collection 和原子切换继续作为运维安全机制。
- 不接入司法解释。本阶段法规范围仍为已审核的十部现行法律及其必要历史版本链。
- 不改变答案生成、授权范围或现有无日期查询的成功路径。

## 架构和数据流

请求带 `case_date` 时，查询层将日期传入版本链选择服务。服务只返回一个有效、可索引的链；由其版本标识解析对应 collection，并将相同的版本溯源信息写入响应的 `version_assumption` 和每条证据元数据。缺日期时，查询层用当前日期调用同一服务并追加假设提示。

前端从查询响应读取 `version_assumption` 与证据元数据：若有适用法规，显示法律名、版本、生效区间、官方来源链接和内容哈希缩写；时间线仅展示 API 返回的版本链条目，不自行推导日期。

案例来源审计保持在案例服务层：从已存字段计算布尔完整状态及缺失字段列表，API 仅传递结果，前端据此显示“资料完整”或具体缺项。

## 错误处理

- `case_date` 格式无效：请求校验失败。
- 某法律在该日期无可索引版本：返回 `NO_INDEXABLE_VERSION_ON_QUERY_DATE`，不混入当前版本。
- 日期命中多条有效版本：返回 `AMBIGUOUS_EFFECTIVE_VERSION`，要求管理员修复版本链。
- 证据没有版本元数据：卡片显示“该来源未登记版本信息”，不虚构字段。
- 案例字段为空：返回缺失字段，不影响现有案例查询与页码溯源。

## 验收

- 带日期和不带日期的查询均有自动化测试，分别验证版本选择和假设提示。
- API 响应含版本溯源字段，前端测试验证版本卡片与时间线渲染。
- 案例来源接口能针对完整和不完整记录输出准确 `missing_fields`。
- 既有法规版本链、查询、案例 API 测试继续通过；新增测试先失败后通过。
