# v2.4 会话记忆与个性化设计

日期：2026-10-01  
状态：已确认，待实施

## 目标与边界

LexRAG 的法律咨询应支持同一用户在同一会话中的连续追问：服务端保存会话、恢复历史，并在生成下一轮回答时使用受控上下文。用户可浏览、搜索、重命名和归档自己的会话；系统基于真实使用记录给出可解释的法规、案例和常见问题推荐。

本版本不引入 PostgreSQL、LangGraph Checkpointer 或新的 LLM 推理链。现有 MySQL 与固定证据工作流继续承担持久化和法律结论校验。用户历史只辅助理解问题，不能替代本轮检索证据。

## 现状与决策

当前 `chat_history` 已以 `session_id` 保存问答，但 `/query` 将记录写给硬编码用户 `1`，前端会话列表只存在内存，刷新后无法恢复。主问答链是 `LegalEvidenceWorkflow`，不是 LangGraph `StateGraph`，所以接入 `PostgresSaver` 必须增加 PostgreSQL 并重构稳定工作流，收益不足。

采用 MySQL 会话服务：增加明确的会话实体和用户画像摘要；`chat_history` 保持每轮不可变审计记录；在 API 层装配最近上下文并将其传给回答节点。保留既有证据账本、法规范围隔离、引用校验和缓存规则。

## 数据模型

### sessions

新增 `sessions` 表：

- `id`：UUID 字符串主键；由服务端生成。
- `user_id`：外键 `users.id`，删除用户时级联删除。
- `title`：最长 120 字；首条问题生成初始标题，用户可重命名。
- `created_at`、`updated_at`：用于排序和审计。
- `is_active`：软删除/归档标记；归档会话不接受新提问。

索引覆盖 `(user_id, is_active, updated_at)`。`chat_history.session_id` 逻辑关联该表；不改写既有历史记录，以免损害审计可追溯性。

### user_profiles

新增每用户一条的 `user_profiles`：

- `user_id`：主键兼外键。
- `law_area_counts`：按知识库 slug 的计数 JSON。
- `intent_counts`：按 v2.1 路由意图的计数 JSON。
- `updated_at`。

仅在本轮回答引用校验通过后更新，避免失败、降级或无证据回答污染画像。

## API 契约与权限

新增受 JWT 认证保护的会话路由：

- `POST /sessions`：创建空会话；可选标题。
- `GET /sessions`：列出当前用户的活跃会话，支持 `q` 标题搜索。
- `GET /sessions/{id}`：返回会话元数据和按时间排序的消息。
- `PATCH /sessions/{id}`：重命名当前用户会话。
- `DELETE /sessions/{id}`：软归档当前用户会话。
- `GET /recommendations`：返回当前用户的推荐及其依据领域。

`/query` 改为 JWT 认证接口：请求未提供 `session_id` 时先创建会话，提供时必须属于当前用户且仍为活跃状态。所有历史写入使用真实 `current_user.id`。不存在、归档或他人会话均不能写入或读取；返回 404，避免泄漏资源是否存在。

## 受控记忆与证据流

每次问答按以下顺序运行：

1. 验证用户、会话及所选知识库。
2. 从当前用户、当前会话加载最近五轮历史；每轮包含问题、回答和其中 `is_verified=true` 的引用标识。不得读取其他用户或其他会话。
3. 本轮仍按 v2.1 执行规划、路由、检索、证据账本、回答与引用校验。
4. 回答生成器接收“历史上下文 + 本轮证据”。Prompt 明确规定：历史仅用于解释代词、延续话题和理解上下文；新法律结论和引用只能来自本轮证据账本。
5. 校验通过后，持久化问答、更新时间、更新画像；未通过的回答不更新画像，也不作为可带入的已验证引用。

历史上下文最多五轮，并在服务端截断每轮文本，防止无界 Prompt 膨胀。API 元数据仅报告 `memory_turns_used`，不暴露其他历史或内部 Prompt。

语义和精确缓存的作用域加入 `session_id`，避免上一轮上下文不同却复用旧回答。

## 推荐规则

推荐不调用 LLM：根据画像中计数最高的、当前仍为 `READY` 的知识库，返回该法律领域的预设常见问题、法规浏览入口和案例检索入口。无有效画像时返回民法典通用入口。响应含 `based_on_law_area`，让推荐的原因可见、可验证。

## 前端体验

聊天页改为三栏：左侧为可搜索的会话列表（新建、重命名、归档），中间为现有对话区，右侧继续显示法条溯源。选择会话通过 `/chat/:sessionId` 路由加载历史；新建会话路由至 `/chat`。发送第一问后更新 URL、标题和列表排序。页面底部显示推荐入口，但不把推荐包装成法律结论。

## 错误处理

- 网络或历史加载失败：不清空当前已渲染消息，显示可重试错误。
- 会话归档、找不到或无权访问：前端提示会话不可用并返回新会话入口。
- 画像更新失败：记录告警但不影响已校验的问答响应。
- 查询本身仍遵循 v2.1 的证据不足提示和一次受控修复；记忆不绕过该分支。

## 测试与验收

先写测试、确认失败后实施。至少覆盖：

- 会话仅能被所属用户列出、读取、重命名和归档。
- 新会话与首问的标题/更新时间行为；归档后拒绝继续提问。
- 历史只取最新五轮，排序稳定，未校验引用不进入记忆上下文。
- 回答生成器收到历史上下文，但引用校验仍只接受本轮账本证据。
- 缓存按会话隔离。
- 仅通过校验的问答更新画像；无画像时推荐安全默认项。
- Vue 类型检查和生产构建通过。

真实验收以两个登录用户、两个会话、连续追问和刷新恢复为样本；记录实际 API 响应、会话隔离、引文校验结果和端到端延迟。没有人工标注时，不宣称记忆提升了法律准确率。
