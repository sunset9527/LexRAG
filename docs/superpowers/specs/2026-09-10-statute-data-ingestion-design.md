# v1.9-02 核心法规数据接入设计

**状态：已确认，待实现**  
**日期：2026-09-10**  
**范围：LexRAG v1.9 模块 1——核心法规数据接入**

## 目标

把用户提供的本地法律文档纳入一条可重复执行、可核验、可追溯的法规接入管线，并写入已有的多知识库架构。完成后，刑法、劳动法、劳动合同法、公司法、专利法、商标法和著作权法都能作为独立法规库被浏览、切换和检索。

本次将 `E:\\个人发展\\002职业\\项目1：RAG法律` 中用户确认的 EPUB/PDF 资料视为官方法律文本来源。系统不联网抓取或替换原始内容。

## 非目标

- 不接入指导案例、典型案例、司法解释或裁判文书。
- 不做 PDF/Word 上传、OCR 或异步文档状态机。
- 不实现法规版本链或新旧条文差异比较。
- 不改变已有检索、Agent 推理、前端知识库切换的语义。
- 不修改或重新索引 `civil-code`（民法典）知识库。

## 方案选择

采用“原始资料保留 + 清洗文本分层 + 清单驱动导入 + 独立验收”的管线。

```text
用户提供的 EPUB/PDF
  -> data/laws/raw/<source-id>/        原始提取文本与来源元数据
  -> data/laws/<law-slug>.txt          清洗后的单部法律文本
  -> LawParser + StructuredLawChunker
  -> KnowledgeBaseService
  -> kb_<law-slug> Chroma collection
```

导入脚本不直接操作 Chroma 或数据库，而是调用 `KnowledgeBaseService`。这与 v1.9-01 的边界一致，确保状态、统计、失败信息与 API 展示保持一致。

## 文件与来源元数据

新增以下受版本控制的文本资产：

```text
data/laws/raw/
  manifest.json                 # 原始来源登记
  <source-id>/extracted.txt     # 从一个原始文档提取的未清洗文本
data/laws/
  criminal-law.txt
  labor-law.txt
  labor-contract-law.txt
  company-law.txt
  patent-law.txt
  trademark-law.txt
  copyright-law.txt
```

`manifest.json` 对每个原始资料记录：`source_id`、原始文件名、原始文件 SHA-256、提取时间、用户确认的来源属性、包含法律清单和提取工具版本。对每份清洗后文本记录：对应 `source_id`、清洗后文本 SHA-256、法律名称、首尾条号与法条数量。

原始 EPUB/PDF 文件本身不复制进项目仓库，避免不必要的大文件重复；来源清单保存其原始绝对路径和哈希，以便本机复核。若路径失效，已保留的提取文本和哈希仍可供复现清洗、解析和入库。

## 清洗和拆分规则

1. 从 EPUB/PDF 提取 UTF-8 纯文本；保留原始提取产物，不在其上修改。
2. 删除目录、页眉页脚、出版说明、注释、索引、案例、量刑标准等非现行法条正文内容。
3. 将每部法律拆为独立文件；文件第一行必须是法律全称，正文保留编、章、节和逐条条文。
4. 统一空行、全角空格和断行；不得合并不同法条或改写法条文字。
5. 使用 `LawParser` 解析清洗文本；解析失败、无条文、条号重复、条号不递增或首末条号异常时，停止该法律的入库。

清洗属于数据整理，不对法律条文作语义修订。发现源文本缺段或疑似注释混入时，应让该库构建失败并报告，而不是用推测内容补齐。

## 导入命令与流程

新增统一命令行脚本 `scripts/ingest_statutes.py`，支持：

- `--law <slug>`：只导入一部指定法律；
- `--all`：依次导入清单中全部法规；
- `--validate-only`：只执行清洗文本的解析和质量校验，不访问 MySQL 或 Chroma；
- `--force`：仅对指定的已注册法律重建目标 collection；不影响其他知识库。

导入一部法规的步骤：

1. 读取该 `.txt` 与清单条目，并执行解析和质量校验。
2. 幂等创建对应 `KnowledgeBase` 注册记录；若已有记录，校验其名称、领域和 collection 是否与清单一致。
3. 调用 `KnowledgeBaseService.rebuild_knowledge_base(slug, content=...)`。
4. 打印并持久化本次验收摘要：法条数、chunk 数、首尾条号、源文件哈希、清洗文本哈希、知识库状态。

任何单库失败不会清除其他库；`--all` 汇总全部成功和失败项，并以非零退出码标记有失败。

## 验收标准

每个法规库必须同时满足：

1. 清洗文本来源可由 `manifest.json` 追溯到用户提供原文件及 SHA-256。
2. `LawParser` 至少解析出一条条文；法条号无重复，按严格递增顺序排列。
3. 验收规则记录实际的法条数、首条号和末条号；不预先编造固定数字。
4. 数据库中的知识库状态为 `READY`，`document_count` 与解析条数一致，`chunk_count` 大于等于 `document_count`。
5. 在该库的 Chroma collection 中读取出的所有文档，其 `law_name` 和 `article_id` 均对应当前法律；不得混入同源 EPUB 中其他法律。
6. 通过现有 API/前端选择该知识库后，法规浏览和检索只展示该库的条文。

对于劳动合同法：若用户提供文本没有完整正文，验收结论必须是明确的“未接入：来源资料不含完整文本”，不得把劳动法内容误标为劳动合同法。

## 测试策略

按照测试先行实现；所有新行为先以 fixture 级小文本验证，避免测试加载 BGE-M3 或依赖真实 Chroma 数据。

1. 来源清单校验：文件存在、哈希格式正确、每个法律配置唯一且字段完整。
2. 清洗文本校验：正文标题匹配、解析结果条号递增且无重复；目录/注释样本不产生伪条文。
3. 拆分隔离：从同一来源得到的两个法律只包含各自的 `law_name` 和法条范围。
4. 单库导入：正确创建/复用注册记录，只重建自己的 collection，并更新统计。
5. 失败隔离：一部法规校验失败时不调用索引器、不将其标记为 `READY`，其他已就绪库不受影响。
6. 批量导入：成功项和失败项分别汇总，退出状态可由 CI 判断。

最终执行完整 Python 测试套件，并在真实本地 BGE-M3 环境运行一次 `--validate-only` 和一次单库/全量导入；实际统计写入验收记录。

## 演示路径

1. 展示 `manifest.json` 中刑法或公司法的来源文件名与 SHA-256。
2. 执行 `--validate-only --law company-law`，显示解析出的条数、首末条号和清洗文本哈希。
3. 执行单库导入，展示状态从 `EMPTY`/`FAILED` 变为 `READY` 及真实的 chunk 数。
4. 在知识库管理页切换至该法律库，法规浏览页展示真实条文。
5. 用一个与该法律相关的问题检索，展示返回引用全部来自 `kb_company_law`（或被演示的目标库）。

## 风险与边界

- EPUB 可能同时包含注释、案例和多部法律，必须先拆分、清洗、校验，不能整书入库。
- 来源文件名中的出版年份不必然等于法律现行版本；本模块只记录文本所载版本线索，不声称为实时最新版本。版本时效查询留给模块 5。
- 解析器只识别标准“第…条”格式；若某部文件排版不符合规则，应为该来源新增小范围预处理，不扩张为通用文档解析中心。
