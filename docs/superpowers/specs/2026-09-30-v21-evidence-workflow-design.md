# LexRAG v2.1：证据驱动法律工作流设计

**状态**：已确认；代码与自动化验证完成。2026-09-30 因未配置有效 LLM Key、Redis 未启动，经决定跳过真实 LLM 端到端验收。  
**日期**：2026-09-30

## 目标与边界

v2.1 将当前由 ReAct Agent 自主选择工具的线性问答链，升级为一个单一、受控、可观测的法律证据工作流。工作流的每个节点具有固定职责和明确的输入输出；不创建 Research、Graph、Answer、Reflection 等相互对话或自行规划的多 Agent。

本版本的目标是让每个对外回答满足三项约束：

1. 回答中出现的法条引用必须来自本次请求、当前选定知识库的证据集合。
2. 引用的法律名称与条号必须能被规则校验；校验失败只允许一次基于现有证据的受控修复。
3. 前后端能够获得不含敏感内容的节点轨迹、检索数量、校验结论和耗时，并能在人工核验样本上计算真实质量指标。

本版本不实现合同审查、合规检查、文书生成、OCR、用户画像或新的 PostgreSQL 部署。`v2.2+` 的场景功能复用本工作流的证据与校验边界。现有 ReAct 实现保留在代码库中，直到新工作流通过回归验证后再决定是否移除，不在本版本做无关清理。

## 现状与问题

- `src/agent/workflow.py` 使用 `create_react_agent` 和模块级工具注册表；工具调用路径由 LLM 决定，难以固定检索范围和复现执行轨迹。
- 当前 `/query` 每次为选定法规库构造 `LawRetriever`，但没有将案例、图谱检索或检索来源统一为回答可消费的证据对象。
- `SelfVerifier` 在“条文未收录”或校验异常时软通过，且校验基于回答中提取到的引用再回查；它不能阻止生成阶段引用本次未检索到的条文。
- `QueryResponse.metadata` 已用于缓存信息，适合向后兼容地新增工作流轨迹摘要；不改变既有缓存作用域和 API Key 不落库的约束。

## 方案选择

采用 **Evidence-First 单工作流**：固定节点编排检索、证据账本、回答和验证；只有回答生成与规则无法覆盖的逻辑复核使用 LLM。相比多 Agent 协作，它的状态与失败分支可预测、延迟和 Token 上限可控，且更容易对法律引用做回归测试。

LangGraph 仅作为状态机/DAG 编排工具使用，不使用 `create_react_agent`。初期轨迹写入现有查询响应和聊天历史 metadata；不引入 PostgresSaver。执行轨迹的长期独立存储留待确有审计需求的版本设计。

## 架构与数据流

```text
QueryRequest（单一 READY 知识库）
  → planning_node（复杂问题才拆解；简单问题跳过）
  → routing_node（factual / comparative / procedural / analytical / emergency）
  → retrieval_fanout（法条必跑；按路由附加案例、图谱）
  → evidence_ledger（归一化、去重、排序、作用域标记）
  → answer_node（仅消费证据账本）
  → citation_verifier（确定性规则校验；可选一次 LLM 逻辑复核）
  ├─ 通过 → QueryResult
  └─ 失败且未修复 → repair_node（最多一次）→ citation_verifier
                                      └─ 仍失败 → 证据不足的安全回答
```

### 1. 状态与证据账本

新增工作流专用状态模型和 `EvidenceItem`，至少包含：`source_id`、`source_type`（`statute` / `case` / `graph`）、`knowledge_base_slug`、`law_name`、`article_id`、`content`、`score`、`retrieval_path` 与 `source_position`（存在时）。

`evidence_ledger` 的唯一键为 `source_type + knowledge_base_slug + source_id`。同一证据来自多条路径时保留路径集合与最佳分数；不得以跨知识库同条号合并。账本只保存本次请求的证据，作为回答和校验的唯一允许引用集合。

### 2. 拆解、路由与检索

- `planning_node` 以结构化 JSON 输出子任务与依赖；只在复杂度阈值达到时调用。JSON 解析、LLM 超时或结构无效时降级为原问题的单任务，不中断请求。
- `routing_node` 产出固定类型和需要执行的检索路径。基础法规检索永远执行；案例和图谱仅在路由需要且相应检索器可用时执行。路由失败时使用 `factual`，只执行法规检索。
- `retrieval_fanout` 使用 v2.0 的原问题、多候选改写、HyDE 与 RRF 法条检索能力。案例/图谱检索失败在轨迹中记录为降级，不阻断法规路径。
- 现有 `/query` 的单知识库约束保持不变。法律名称、条号和知识库 slug 从检索结果 metadata 取得；缺失必要身份字段的条文结果不得进入可引用账本。

### 3. 回答与校验

- `answer_node` 的 Prompt 包含带稳定引用标识的证据账本，并要求以 `【法律名称第N条】` 引用。Prompt 明确禁止引用未提供的证据，并要求无充分证据时说明限制。
- `citation_verifier` 首先解析回答中的法条引用，并在账本中按 `law_name + normalized_article_id + knowledge_base_slug` 匹配。不存在、名称不一致、条号不一致、无引用或账本为空均为失败；不会再把“未收录”或校验异常视为通过。
- 当规则校验通过而回答含有需要解释的法条结论时，可配置一次 LLM 逻辑复核；LLM 不可用、输出无效或超时只记录 `logic_review=skipped`，不把它伪装成通过。
- 规则校验失败时，`repair_node` 只能访问原问题、验证问题和同一份账本，最多生成一次替代回答。第二次规则失败返回固定的“现有证据不足以支持可靠结论”说明及已验证引用，禁止输出未经验证的法律结论。

### 4. API、轨迹与前端

- 保持 `POST /query` 的请求契约和缓存行为。`QueryResponse.metadata` 追加 `workflow_version`、`workflow_status`、`verification_attempts`、`evidence_count`、`verification_summary` 与脱敏 `workflow_trace`。
- 每条轨迹只包含节点名、状态、耗时、输入/输出数量、降级原因和校验结论；不得包含 API Key、Authorization 原文、HyDE 文本、完整 Prompt 或完整用户问题。
- 前端聊天页在不影响已有回答和引用卡片的前提下，展示节点时间线及“检索/校验”摘要；失败和降级以事实性文案提示，不展示伪造的推理内容。

## 错误处理与安全边界

- 没有可引用法条证据时，不调用自由生成来给出确定性法律结论；直接返回证据不足说明和下一步建议。
- 工作流任一可选节点失败时保留已成功的法规检索证据，并将失败原因写入轨迹摘要。
- 引用校验器异常应返回明确的 `verification_status=error`，不作为通过结果缓存；不会让异常校验的回答进入精确或语义缓存。
- 遵循现有免责声明：系统提供法律信息参考，不构成法律建议。

## 测试策略与完成标准

所有生产实现严格遵循 Red → Green → Refactor；每个新行为先以失败测试固定。

1. `EvidenceItem` 与账本：验证同一来源多路径合并、跨知识库不合并、无身份字段的证据不可引用。
2. 路由与降级：验证简单问题跳过拆解、路由失败仅法规检索、可选案例/图谱失败不阻断。
3. 引用校验：验证只接受账本中的同库同法律同条号引用；无引用、伪造条号、错误法律名、校验异常均不能通过。
4. 受控修复：验证仅执行一次，修复后再次失败时返回证据不足回答，不进入缓存。
5. API 契约：验证 metadata 的脱敏轨迹、工作流失败响应和缓存只写入通过的结果；既有 v2.0 缓存/API 测试继续通过。
6. 前端：为轨迹摘要的类型、渲染和降级提示补测试或等价构建检查。
7. 指标：在人工核验的固定样本上输出样本数、引用准确率、证据覆盖率、无证据断言率、校验拦截/修复率和端到端延迟；不得预设结果或修改样本以提高指标。

完成标准是：新增与既有后端测试通过、前端生产构建通过、真实评测报告可审计，且路线图只记录实际运行过的结果。

## 分阶段交付

1. 新工作流状态、证据账本与确定性引用校验器的测试及实现。
2. 结构化拆解、路由、法规/案例/图谱检索扇出和降级轨迹。
3. 回答节点、一次受控修复、`/query` 接入及缓存安全边界。
4. 聊天页工作流摘要与轨迹展示。
5. 全量回归、真实人工核验评测、README 和迭代记录同步。
