## 4. Architecture facts at the Stage 0 baseline

### Main query path

At the Stage 0 baseline, `POST /query` constructed and called `LegalEvidenceWorkflow`, a deterministic Python workflow. Its behavior included planning, routing, statute retrieval, optional case and graph retrieval, an evidence ledger, answer generation, citation verification, one controlled repair attempt, and evidence-insufficient degradation.

It was not a LangGraph `StateGraph` at that baseline. The LangGraph/ReAct code under `src/agent/` was and remains a legacy path that does not carry the main `/query` request. The completed Stage 1 migration is recorded in section 9 without rewriting this historical snapshot.

### Data and runtime dependencies

- MySQL: users, organizations, permissions, sessions, prompts, jobs, audit metadata, usage, knowledge-base metadata, and law-update state.
- Chroma: separate statute, case, and user-document collections.
- Redis and Celery: asynchronous document and scenario tasks.
- BGE-M3: local 1024-dimensional embedding model; the current Windows path is machine-specific and is not a valid container default.
- External LLM: supplied at runtime for answer generation and selected workflow functions.
- Vue 3 frontend: product workbench; the frontend code itself was not part of the large Stage 0 working-tree split.

## 7. Known risks carried into later stages

1. `/query` is not yet a LangGraph `StateGraph`; documentation previously overstated this.
2. `api.py` logs the raw query, and legacy agent modules also log raw query text.
3. `X-Base-URL` currently validates only HTTP(S) shape; it does not enforce provider allowlists, private-address blocking, DNS checks, redirects, or dangerous-port restrictions.
4. `/verify/{query_id}` reads process-local `query_results` and does not establish persistent query ownership.
5. Legacy `/upload`, graph, and case read routes require a deliberate public/private product boundary and consistent organization authorization.
6. Docker Compose cold start, empty-volume bootstrap, model mounting, readiness, migrations, and restart recovery are not accepted end to end.
7. Legal-source authority, effective dates, manifests, judicial interpretations, and version selection remain incomplete.
8. The eight-law 100-row snapshot lacks valid per-row review evidence.
9. Pydantic v2 class-config and dependency deprecation warnings remain in the test output.
10. Several tests leave SQLite connections open, producing `ResourceWarning`s.
11. The frontend production build succeeds but contains two chunks larger than 500 kB after minification.

## 9. Stage 1 follow-up: LangGraph main-chain migration

Stage 1 was completed locally on 2026-10-18 at code commit `697a2d8`. This does not rewrite the Stage 0 snapshot above; it records the later resolution of Stage 0 risk 1.

- `/query` now calls `LegalEvidenceWorkflow.invoke()`, which executes one module-level compiled LangGraph `StateGraph`.
- The graph has explicit planning, routing, mandatory statute retrieval, optional case and graph retrieval, evidence-ledger, answer, citation-verifier, repair, finalize, and evidence-insufficient nodes.
- Conditional edges enforce at most one repair attempt. Missing statute evidence and a second verification failure remain non-cacheable.
- Request-scoped retrievers and LLM-backed callables are passed through LangGraph runtime context; the compiled graph does not retain request credentials or mutable request state.
- Conversation history is carried separately as non-evidence context and is never inserted into the Evidence Ledger.
- `ainvoke()` and `astream_events()` wrappers are present for later streaming integration. The legacy `src/agent/` ReAct module remains non-active and is labeled accordingly.
